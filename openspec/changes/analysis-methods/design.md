## Context

snake-eyes is a JSON-RPC analyzer that Gaze spawns as a subprocess. After issue #3 (`taxonomy-and-discovery`), the server answers `initialize`, `shutdown`, and `discover`, and ships the 48-type `SideEffectType` taxonomy, the `Effect`/`FunctionRecord` models, and `discover()`. The three required protocol methods that actually produce analysis — `analyze`, `complexity`, `coverage` — still return `-32601`.

This change implements those three methods by lifting proven analysis code from `mpeter/gaze-py` (Apache 2.0), adapting it to Python-native AST semantics, and wiring it to the existing server dispatch. The work is constrained by the Snake Eyes constitution (Protocol Fidelity, Detection Accuracy, Python-Native Analysis, Testability, Analysis Safety), the Gaze protocol v1.1.0 contract, and the CI gates (`ruff`, `mypy --strict`, `pytest --cov-fail-under=85`, `uv sync --locked`).

Existing building blocks this design reuses without modification: `discovery.discover(root_path, patterns) -> DiscoveryResult` (POSIX-relative sorted `.py` paths split into `source_files`/`test_files`); the frozen `Effect`/`FunctionRecord` dataclasses and `function_record_to_dict()` (omits `None` optionals); and the `Server`/`RpcError`/`DEFAULT_DISPATCH` handler pattern.

## Goals / Non-Goals

**Goals:**
- Implement `analyze`, `complexity`, and `coverage` so each returns protocol-shaped JSON conforming to Gaze v1.1.0.
- Detect every `SideEffectType` value that has a Python analogue via normative, deterministic AST rules — the original taxonomy types plus 10 new Python-specific types.
- Reuse Python's own parsing infrastructure (`ast`, `symtable`) and lifted gaze-py logic instead of reimplementing Python semantics or adding heavy dependencies.
- Keep the analysis engine (`detector`, `complexity`, `coverage-parser`) testable in isolation, independent of the JSON-RPC layer.
- Preserve gaze-py provenance on all lifted files.

**Non-Goals:**
- `classify_signals` and `test_mapping` methods (remain unimplemented; capability flags stay `false`).
- Streaming (`analyze/stream`), CRAP/GazeCRAP/quadrant math, and classification labels on effects — Gaze owns these.
- Running the analyzed project's test suite or invoking `coverage run` — coverage data is read, never produced.
- astroid-based name/type inference and cross-module resolution (a later change).
- Faking effect types with no Python analogue (`ChannelClose`, `DeferredReturnMutation`, `AtomicOp`, `CgoCall`, `Panic`, `UnsafeMutation`) — none of these are detected in v1.

## Decisions

**D1 — Lift gaze-py's complexity and detector rather than rewrite or add radon.** `src/gaze_py/analysis/complexity.py` logic is lifted into `src/snake_eyes/analysis/complexity.py` (McCabe walk over the `ast`) and then adapted to pass project gates: full type annotations for mypy --strict, ruff format, and import sorting, retaining provenance headers (gaze-py copyright + Apache-2.0 §4(b) change notice, e.g. `# Modified 2026 by zero-dot-force: extended with Python-specific detection; Go-only pattern lists removed.`). Similarly `src/gaze_py/analysis/detector.py` is lifted as the detector core and then extended with the same gate-compliance adaptation. This honors Python-Native Analysis and avoids a `radon` dependency for a computation the lifted code already performs. Alternative considered: depend on `radon` for complexity — rejected because it adds a dependency for capability we already inherit, and mixing radon's function model with our AST walk risks `package`/`line` drift.

**D2 — Detector exposes both `analyze_path` and `analyze_source`.** `analyze_path(root_path, patterns) -> list[FunctionRecord]` is the production entry that runs discovery and reads files; `analyze_source(source, filename, package) -> list[FunctionRecord]` analyzes a single in-memory source string. The second exists specifically for Testability: every detection rule can be unit-tested against a fixture string without materializing a tree or spawning the server. The method handlers call `analyze_path`; unit tests call `analyze_source`.

**D3 — All three methods share `{root_path, patterns}` and the discovery flow.** No method accepts a file list. `analyze` and `complexity` operate on the analyzed file set, which is the ordered concatenation of the sorted `source_files` then `test_files` from `discover()`, de-duplicated preserving first occurrence (never a set union); test files are intentionally included in both `analyze` and `complexity`. `coverage` uses discovery to bound which files it maps. Param validation mirrors the existing `_discover` handler: `root_path` must be a string (missing/invalid → `RpcError(INVALID_PARAMS, ...)` → `-32602`); `patterns` must be a list of strings when present. `FileNotFoundError` from `discover()` maps to `-32602`. Alternative considered: per-method bespoke params — rejected for protocol consistency and to reuse one validation path.

**D4 — `package` is the dotted module path derived from the file path relative to `root_path`.** Strip the `.py` suffix, replace `/` with `.`, and drop a trailing `.__init__` so `pkg/__init__.py → pkg`. This derivation is implemented by ONE shared `derive_package` helper (`PACKAGE_DERIVATION`) used by `detector.analyze_path` and `complexity` only — no duplication. `coverage` result rows use `file` + `function` (no `package`) per the protocol schema, so coverage does NOT use `derive_package`. The shared-helper mapping (post-refactor accurate state): the stat / `S_ISREG` / byte-cap guard is centralized in `is_analyzable_file`, shared by all three modules — detector and complexity via the `iter_source_files` reader, coverage directly from its own per-file span reader — so no module re-implements the guard logic; `iter_source_files` (the safe-file reader that yields `(rel_path, source, tree)`) is used by detector and complexity only, not coverage; `enumerate_functions_with_spans` (per-function AST walk mapping line spans to function names) is used by coverage only; `derive_package` is used by detector and complexity only; `ordered_file_list` is used by all three.

**D5 — Coverage lookup order is `coverage.json` then `.coverage`; missing data is an empty result, not an error.** `parse_coverage` first looks for `root_path/coverage.json` (a coverage.py JSON report parsed with stdlib `json`, using `files.<path>.executed_lines`/`missing_lines`); if absent it loads `root_path/.coverage` via `coverage.Coverage(data_file=...).load()` then `Coverage.analysis2(filename)` (which returns executable statements + missing lines, so `total_stmts` is computable) — NOT `CoverageData.lines()`, which returns only executed lines and would force ~100%. If neither exists `parse_coverage` returns `[]` (a bare empty list — NOT `{"functions": []}` directly). Lines are mapped to functions with the same AST start/end spans used elsewhere: `total_stmts` counts statement lines within `[start_line, end_line]`, `covered_stmts` counts those that were executed, and `percentage = round(covered/total*100, 1)` when `total > 0` else `0.0`. Analysis Safety forbids ever running the analyzed suite. **Failure granularity:** a whole-datafile load/parse failure (`json.JSONDecodeError`, `sqlite3.DatabaseError`, top-level `CoverageException` raised by `load()`, or `KeyError`/`TypeError` for JSON-valid-but-wrong-shape data) causes `parse_coverage` to return `[]` (empty list); the coverage RPC handler performs the sole `{"functions": <list>}` wrap when building the JSON-RPC result. A per-file `Coverage.analysis2()` failure (e.g. `NoSource`, `NotPython`, or other `CoverageException` subclass for one moved/generated source file, or any entry in `BROADENED_EXCEPTIONS` including `MemoryError`) skips THAT file and continues with a stderr diagnostic — valid files still contribute coverage rows. Before calling `Coverage.analysis2()`, each candidate file is also run through `S_ISREG` + byte-cap check (same as the detector) and wrapped in `BROADENED_EXCEPTIONS` plus `CoverageException` subclasses for per-file skip-and-continue.

Coverage path confinement: `parse_coverage` runs `discover(root_path, patterns)` FIRST and maps coverage data ONLY for files in the discovered set. Any path from `coverage.json` is `resolve()`d and confined within `root_path` (never opened verbatim). `coverage.json` keys are normalized to root-relative POSIX paths. A nonexistent `root_path` raises `FileNotFoundError` → `-32602` before any file lookup. Malformed or incompatible data (`json.JSONDecodeError`, coverage `CoverageException`, `sqlite3.DatabaseError`) return an empty result `{"functions": []}`.

**D6 — `ErrorSignal` is dual-emitted with `ErrorReturn` for every `raise` — with a SystemExit-family carve-out.** Every `raise` statement emits `ErrorSignal`. A `raise` of an instance, call, or name also emits `ErrorReturn` at the same location. A bare `raise` (re-raise) emits BOTH `ErrorReturn` and `ErrorSignal`. **SystemExit-family carve-out:** `raise SystemExit`, `raise SystemExit(...)`, `sys.exit(...)`, and `os._exit(...)` emit `ProcessExit` + `ErrorSignal` and do NOT emit `ErrorReturn` — `ProcessExit` provides the exit facet and `ErrorReturn` is absent. `assert` is NOT an effect in v1. This is required protocol behavior (the two types describe distinct facets Gaze scores separately), so both rows are emitted rather than collapsing to one.

**D7 — Ambiguous constructs are reported, never dropped.** The pure-builtin allowlist is explicitly enumerated (referencing the gaze-py constant). `eval`, `exec`, and computed dynamic calls (`getattr(obj, name)()`) emit the most likely effect when a known pattern matches; otherwise they emit `CallbackInvocation` with `detail={"confidence": "ambiguous"}`. A call to a name not on the allowlist and not matching a known effect pattern falls back to `CallbackInvocation` with `detail={"confidence": "ambiguous"}` — never silently dropped. A statically-resolvable pure local call is NOT an effect. This is the direct expression of Detection Accuracy's "ambiguity over omission."

**D8 — Effects carry no classification; `target` and `detail` are optional.** Each serialized effect always includes `type`, `description`, and `location`; `target` and `detail` are OPTIONAL and omitted when not applicable (per `function_record_to_dict`). `location` is always `"file.py:line:col"`. Gaze owns contractual-vs-incidental classification, so snake-eyes never sets a `classification` field. `detail` is reserved for Python-specific metadata only (e.g. `{"exception_class": "ZeroDivisionError"}` or `{"confidence": "ambiguous"}`), and is omitted when empty.

**D9 — Parse-error files are skipped and the request continues; no `errors` array is added.** When `ast.parse` raises `SyntaxError`, `ValueError`, or `RecursionError` (raised during `ast.parse` or during AST traversal) on a file, or when reading a file raises `OSError` (e.g. `PermissionError`) or `MemoryError` (raised during AST traversal of a pathologically large structure), that file contributes no functions and analysis proceeds to the next file. The analyzer also reads only **regular files** (`stat` + `S_ISREG` check before `open()`): non-regular files (FIFOs, devices, sockets) are skipped with a stderr diagnostic before `open()` is attempted, and the byte-size cap is derived and enforced from the `stat` result (a PRE-`open()` guard) so a 0-byte FIFO cannot bypass the cap. A per-file diagnostic is written to stderr (never to the stdout JSON-RPC result), with an aggregate count optionally included. The protocol result schema has no `errors` field, so none is invented (Protocol Fidelity). This same BROADENED_EXCEPTIONS tuple — `(SyntaxError, ValueError, RecursionError, OSError, MemoryError)` — applies across all four modules: `detector`, `analyze`, `complexity`, and `coverage`. This keeps a single malformed or unreadable file from failing an otherwise valid `analyze`/`complexity`/`coverage` request.

**D10 — Delete dead Go-only pattern lists; never fake effects without a Python analogue.** Lifted gaze-py constants that no Python rule consumes are removed rather than left as unused code (satisfies the zero-waste mandate and keeps `detector.py` coverage achievable). `ChannelClose`, `DeferredReturnMutation`, `AtomicOp`, `CgoCall`, `Panic`, and `UnsafeMutation` are retained in the `SideEffectType` enum as vocabulary but NOT detected (no reliable Python analogue); the analyzer SHALL NOT fabricate them. The `SideEffectType` enum retains all 48 members (vocabulary), but detection is limited to types with genuine Python semantics.

**D11 — Each `def`/`async def` is its own `FunctionRecord` with an unqualified name.** Nested functions and methods of nested classes each yield a record; the `name` is the bare def name (not `outer.inner`). Two nested defs sharing a name emit two rows distinguished by `line`. Lambdas are not functions and produce no record for `complexity`. Effect attribution prefers `ReceiverMutation` for `self.*`, `PointerArgMutation` for parameters, and `ContainerMutation` for locals/unknown targets.

**D12 — `coverage>=7.0,<8` is the only new runtime dependency.** It is needed to read `.coverage` SQLite data files through a stable public API; the JSON path uses only the stdlib. Added to `pyproject.toml` and locked via `uv.lock`. `radon` and `astroid` are explicitly not added.

**D13 — Resource bounds on untrusted input (Constitution V).** Analyzed files are untrusted. Two fixed constants bound analysis: `MAX_FILE_BYTES = 16 MiB` (a PRE-`open()` byte-size cap derived from `stat`, mirroring the server's `MAX_LINE_CHARS` precedent) and `MAX_AST_DEPTH` (a fixed AST-depth/recursion budget enforced DURING traversal via a bounded `NodeVisitor` and `RecursionError`/`MemoryError` catch — it is infeasible to enforce depth before `ast.parse` is called). Both are fixed constants in v1 and are NOT user-configurable. An unbounded file count is an accepted risk mitigated by Gaze subprocess supervision (Gaze controls the lifetime of the snake-eyes process). A file exceeding a bound is skipped-and-continued (like a parse error), never aborting the whole request; a per-file diagnostic is written to stderr, never to the stdout JSON-RPC result. Large-tree streaming is explicitly deferred to a future `analyze/stream` implementation.

**D14 — Deterministic output ordering.** `analyze` and `complexity` `functions[]` are ordered by `(file, line, name)`; `coverage` `functions[]` are ordered by `(file, start_line, function)` — coverage rows carry no `line`/`name` in the same sense (they use `start_line` and `function` field names per protocol schema). `side_effects[]` within each function are ordered by `(line, col, type)`. The analyzed file set is the ordered concatenation of the sorted `source_files` then `test_files`, de-duplicated preserving first occurrence (never a set union); sentinel-exception collection is a deterministic ordered list, never a set. The same input tree MUST produce byte-identical JSON-RPC output. A byte-identical conformance test and canned schema-conformance request/response pairs are required for `analyze`, `complexity`, and `coverage`.

## Risks / Trade-offs

- P0 false negatives (missing `ReturnValue`, `ErrorReturn`, `ReceiverMutation`, `PointerArgMutation`, etc.) are release-blocking → mitigated by dedicated P0 fixtures (`p0.py`) and per-type assertions on effect type string plus location.
- Dynamic dispatch (`eval`/`exec`/computed `getattr`) can hide real effects → mitigated by D7: always emit an ambiguous `CallbackInvocation` rather than nothing.
- coverage.py data-format drift across versions → mitigated by a floor-and-ceiling constraint (`coverage>=7.0,<8`), preferring the stdlib JSON path, and using only documented API surface for the `.coverage` path.
- Lifted Go-isms (channel/goroutine/atomic vocabulary, gaze-py `se-XXXXXXXX` effect IDs) leaking into Python output → mitigated by D10 (delete dead lists) and by not emitting gaze-py effect IDs in protocol JSON.
- Double-emission between overlapping rules (e.g. `StreamOutput` vs `StdoutWrite`/`StderrWrite`, `ContainerMutation` vs `ReceiverMutation`, `StreamOutput` vs `WriterOutput`) → mitigated by explicit precedence: `print`/`sys.stdout`/`sys.stderr` are covered by `StdoutWrite`/`StderrWrite` and not re-emitted as `StreamOutput`; `self.*`/param targets take precedence over `ContainerMutation`; a `.write` on a concretely-opened or passed-in file object emits `StreamOutput` only — not `WriterOutput` (for a parameter whose file-ness cannot be proven in v1, the default is `WriterOutput`; never double-emit both).
- Coverage line-to-function mapping mismatch (decorators, multi-line signatures) → mitigated by using AST `lineno`/`end_lineno` body spans consistently with the complexity/detector walk and asserting expected covered/total on a canned fixture.
- `analyze`, `complexity`, and `coverage` each re-parse the AST tree (up to 3×); this is accepted as a trade-off of the stateless-per-request design. A per-process AST cache keyed by `(path, size, mtime)` may be added as an optimization in a later change, but it MUST NOT affect output.

## Migration Plan

The change is purely additive to the protocol surface. Deploy steps: (1) add `coverage>=7.0,<8` to `pyproject.toml` and refresh `uv.lock` (`uv sync --locked` must pass in CI); (2) land `complexity.py`, `detector.py`, `coverage.py` with provenance headers; (3) register the three handlers in `DEFAULT_DISPATCH` — `initialize` output is unchanged, so existing Gaze clients need no update and simply stop receiving `-32601` for these methods. Rollback is a straight revert: removing the handlers restores `-32601` and removing the dependency restores the empty dependency set; no persisted state or data migration is involved.
